# MT5–Python–SQLite Integration
## Technical Implementation Roadmap

**Project Objective:** Build a reliable, sequential communication system between MetaTrader 5 and Python, with Python acting as the database manager (SQLite secretary) for MetaTrader.

The implementation is divided into three independent but connected workstreams.

---

# 1. Communication Reliability: MT5 ↔ Laravel ↔ Python

## 1.1 DLL Responsibilities

The existing DLL will use Windows WinHTTP.

The DLL is responsible only for HTTP communication.

It must not implement application-level retry, request tracking, response management, or database logic.

The DLL currently returns its own error codes:

- `-4`
- `-5`

Their exact meanings must be verified from the current DLL source code before implementation.

No DLL modification is planned unless a specific technical requirement makes it necessary.

## 1.2 Persistent Request Tracking on MT5

Before sending any request, MT5 must:

1. Generate a unique `request_id`.
2. Store the request ID and its payload in a local text file.
3. Send the request through the DLL.
4. Keep the request in the text file until successful acknowledgment.

The text file acts as persistent storage for unresolved requests.

A request must never be discarded merely because an HTTP operation timed out or failed.

## 1.3 Request Identification

Every request must have one unique and stable `request_id`.

The same ID must be preserved during all retries and polling operations.

A retry must never generate a new ID for an existing unresolved request.

## 1.4 Python Request Tracking

Python must persist each received request using its `request_id`.

The tracking record must contain:

- `request_id`
- `payload`
- `command_type`
- `status`
- `response`
- `created_at`
- `completed_at`
- `acknowledged_at`

The status lifecycle is:

`pending → completed / failed → acknowledged`

A request must not become acknowledged merely because Python completed its processing.

## 1.5 Response Persistence

Every response generated by Python must be associated with the original `request_id`.

This applies to:

- Quick responses
- Intermediate analysis results
- Final analysis results
- Error responses

Responses must remain available for MT5 retrieval until the corresponding request is acknowledged.

## 1.6 Polling and Recovery

If MT5 does not receive a reliable response:

1. MT5 checks the response store using the original `request_id`.
2. If the response exists, MT5 retrieves it.
3. If no response exists, MT5 resends the original request with the same ID.
4. If communication is still unavailable, the request remains in the local text file.
5. MT5 retries recovery during subsequent polling cycles.

The system must distinguish between a communication failure and an actual processing failure.

## 1.7 Acknowledgment (ACK)

ACK is sent by MT5 after the expected response has been successfully received and consumed.

Python then marks the request as acknowledged.

MT5 removes the corresponding request from its local text file only after receiving confirmation that the ACK operation succeeded.

ACK operations must be idempotent.

## 1.8 Sequential Processing

The system is sequential and non-concurrent.

Only one unresolved application request is allowed at a time.

The next request must not begin normal processing until the previous request has reached its required completion state.

This simplifies request tracking, recovery, response matching, and acknowledgment.

# 2. SQLite Database Secretary

Python acts as the database secretary for MetaTrader.

MT5 sends predefined commands. It never sends raw SQL statements.

Python validates the commands, constructs safe SQL statements, executes them, and returns the results.

## 2.1 The Eight Database Commands

The following eight commands constitute the initial database command protocol.

| Command | Meaning | Description |
|---|---|---|
| `MAKE` | Make Table | Create a table. If it already exists, drop and recreate it. |
| `INSR` | Insert Row | Insert a new record. |
| `SELA` | Select All | Retrieve records from a table, subject to a configurable limit. |
| `SELR` | Select Range | Retrieve records matching a specified range or validated conditions. |
| `LAST` | Select Last | Retrieve the latest N records. |
| `DELR` | Delete Row | Delete the latest record. |
| `CLER` | Clear Table | Delete all records while preserving the table structure. |
| `DROP` | Drop Table | Delete the entire table. |

### Command Details

**MAKE**

- Create the requested table.
- If the table already exists, drop and recreate it.
- Table schema must be defined through validated column definitions.
- The operation must be transactional.

**INSR**

- Insert a record using parameterized SQL.
- Preserve the original data types.
- Return the inserted record ID or an equivalent result.

**SELA**

- Retrieve records from the requested table.
- Support a configurable maximum number of records.

**SELR**

- Retrieve records using validated conditions.
- Support time-based range queries where applicable.

**LAST**

- Retrieve the latest N records.
- Results must be returned in a clearly defined chronological order.

**DELR**

- Delete the latest record based on its defined ordering key.

**CLER**

- Delete all records.
- Preserve the table structure.

**DROP**

- Completely remove the requested table.

## 2.2 Table Naming Convention

The table name identifies the trading symbol.

Examples:

- `EURUSD`
- `GBPUSD`
- `XAUUSD`

The implementation must validate and safely map symbol names to SQLite table identifiers.

MT5 must only access tables that belong to its approved table registry.

## 2.3 Candle Unique Key

The candle identity is defined by:

`TableName + timeframe + candle_time`

The table name identifies the symbol.

Within each symbol table, the combination of:

`timeframe + candle_time`

must be unique.

Examples:

- EURUSD / H1 / candle_time
- EURUSD / H6 / candle_time
- GBPUSD / H1 / candle_time

The database must enforce this uniqueness constraint.

This prevents duplicate candle records when an INSERT request is retried.

## 2.4 Candle Table Structure

Each symbol table must support the following fields:

- `id`
- `timeframe`
- `candle_time`
- `open`
- `high`
- `low`
- `close`
- `volume`

Additional fields must only be introduced when required by the MT5 data contract.

The unique constraint must cover:

`(timeframe, candle_time)`

## 2.5 SQL Safety

Python must validate:

- Table names
- Column names
- Column definitions
- Supported data types
- SELECT conditions
- Record limits

Values must use SQLite parameterized queries.

Raw SQL supplied by MT5 is not permitted.

# 3. Candle Synchronization and Recovery

The purpose of this workstream is to maintain an accurate SQLite representation of the candle history maintained by MT5.

## 3.1 Initial Initialization

The initial history consists of:

- 100 H1 candles
- 20 H6 candles

Total: 120 candles.

Initialization sequence:

1. MT5 collects the initial candle history.
2. MT5 sends an initialization request.
3. Python creates the symbol table using `MAKE`.
4. Python inserts the initial candles using `INSR`.
5. MT5 requests the stored history using `SELA`.
6. MT5 verifies that the stored records match its expected candle history.
7. The initialization request is completed and acknowledged.

## 3.2 Normal Candle Update Cycle

When a new candle forms:

1. MT5 requests the existing candle history using `SELA` or `SELR`.
2. Python returns the stored records.
3. MT5 checks the returned history against its expected data.
4. If the history is valid, MT5 sends the previously closed candle using `INSR`.
5. Python inserts the candle.
6. MT5 verifies the insertion result.
7. The request is completed and acknowledged.

The normal update sends only the newly closed candle, not the entire 120-candle history.

## 3.3 History Validation

MT5 must verify that the database contains the expected historical candles.

Validation must consider:

- Expected candle timestamps
- Expected timeframes
- Missing records
- Duplicate records
- OHLC consistency
- Record ordering

Checking the existence of a single candle is not sufficient to establish that the complete history is valid.

## 3.4 Full Recovery

If a genuine database inconsistency is detected:

1. MT5 stops normal candle updates.
2. MT5 initiates a recovery request.
3. Python recreates the relevant symbol table using `MAKE`.
4. MT5 collects the latest 120 candles.
5. MT5 sends the complete initialization dataset.
6. Python inserts the candles.
7. MT5 retrieves and validates the stored history.
8. Normal candle updates resume after successful validation.

A communication timeout alone must not trigger a destructive table rebuild.

The system must first attempt request recovery through the original `request_id`.

# 4. Implementation Order

Implementation must follow this sequence.

| Phase | Task | Expected Result |
|---|---|---|
| 1 | Inspect the current WinHTTP DLL | Verify HTTP behavior and error codes `-4` and `-5`. |
| 2 | Implement MT5 persistent request storage | Requests survive MT5 restarts and communication failures. |
| 3 | Implement Python request tracking | Every request is stored under its unique ID. |
| 4 | Implement persistent response storage | All responses can be retrieved by request ID. |
| 5 | Implement polling and recovery | MT5 can recover missing responses and safely retry requests. |
| 6 | Implement ACK | Completed requests are explicitly acknowledged. |
| 7 | Implement the eight SQLite commands | Python provides the database secretary interface. |
| 8 | Implement candle initialization | The initial 120 candles are stored and verified. |
| 9 | Implement candle updates | Only the newly closed candle is inserted. |
| 10 | Implement history validation and recovery | Inconsistent history can be rebuilt safely. |
| 11 | Perform failure testing | The complete system is verified under unstable network conditions. |

# 5. Testing Requirements

The implementation is not considered complete until the following tests pass.

### Communication Tests

- Successful request and response.
- HTTP timeout.
- Lost quick response.
- Lost final response.
- Repeated request with the same `request_id`.
- MT5 restart with unresolved requests.
- Lost ACK.
- Repeated ACK.
- Recovery of a previously completed request.

### SQLite Tests

- Create a new table.
- Recreate an existing table using `MAKE`.
- Insert a record.
- Select all records.
- Select a time range.
- Retrieve the latest records.
- Delete the latest record.
- Clear a table.
- Drop a table.
- Attempt to insert a duplicate candle.

### Candle Tests

- Initialize 100 H1 and 20 H6 candles.
- Verify all 120 initial candles.
- Insert one newly closed H1 candle.
- Insert one newly closed H6 candle.
- Verify that previous candles remain unchanged.
- Simulate a lost INSERT response.
- Verify that retrying does not create duplicate records.
- Simulate missing or inconsistent historical data.
- Rebuild and verify the complete history.

---

# 6. Strict Development Rules

1. Implement one phase at a time.
2. Do not start the next phase until the current phase has been tested.
3. Do not modify the DLL unless explicitly required and approved.
4. Do not introduce concurrent request processing.
5. Do not introduce unnecessary database commands.
6. Do not send raw SQL from MT5.
7. Do not generate a new request ID when retrying an existing request.
8. Do not acknowledge a request before its expected response has been consumed.
9. Do not rebuild tables merely because an HTTP request timed out.
10. Do not declare the solution complete without actual execution and test evidence.

## Final Architecture

`MetaTrader 5`

↓

`Local Persistent Request File`

↓

`WinHTTP DLL`

↓

`Laravel Gateway`

↓

`Python Gateway`

↓

`Request Tracking + Response Store`

↓

`SQLite Database Secretary`

↓

`Response Retrieval + Polling`

↓

`MT5 Response Processing + ACK`

**The system must remain sequential, recoverable, persistent, and verifiable.**

**This document is the agreed implementation roadmap. No implementation phase should be skipped or considered complete without verification.**
