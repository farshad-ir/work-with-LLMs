# MT5 Reliable Delivery Protocol
## Protocol for Persistent, Sequential and Recoverable Message Delivery

### 1. Objective

Build an end-to-end reliable messaging protocol between:

- MetaTrader 5
- WinHTTP DLL
- Laravel Gateway
- Python Gateway

The system must tolerate:

- Internet interruptions
- HTTP timeouts
- Lost requests
- Lost responses
- Lost ACK messages
- MT5 restarts
- Laravel restarts
- Python restarts
- Server power failures

No request or response may be lost merely because a component restarts.

### 2. Unique Request Identity

Every MT5 request must receive a unique, persistent request ID.

The request ID is generated by MT5 and must remain unchanged during all retries.

The ID sequence must survive terminal restarts and power failures.

Before transmitting a request, MT5 must persist:

- Request ID
- Request payload
- Creation timestamp
- Current delivery status
- Last retry information

The persistent counter must be updated before the request is transmitted.

A request retry must reuse its original ID.

### 3. Request Identity and Payload Hash

Request ID and payload hash serve different purposes.

- Request ID identifies a specific logical request.
- Payload hash identifies the content of that request.

The same payload may legitimately be sent more than once under different request IDs.

The same request ID must never represent two different payloads.

The server must detect and reject this conflict.

### 4. Durable Server-Side Storage

Python must use persistent storage for its request and response records.

In-memory queues must never be the authoritative storage.

The server must persist:

- Received requests
- Request payloads
- Processing status
- Generated responses
- Response sequence numbers
- ACK status
- Timestamps

A restart must not erase unresolved requests or unacknowledged responses.

Request registration and response registration must use durable database transactions.

### 5. Laravel Delivery Responsibility

Laravel must not report successful application-level delivery until Python has durably registered the request.

If Laravel receives a request but cannot confirm durable registration by Python, it must return an appropriate failure or uncertainty response.

A Laravel restart must not cause an accepted but undelivered request to disappear.

The exact durability mechanism between Laravel and Python must be defined during implementation.

### 6. Response Queue

Every response must have:

- `request_id`
- `response_id`
- `response_sequence`
- `response_type`
- `payload`
- `created_at`
- `acknowledged_at`

Response types include:

- Initial receipt acknowledgment
- Processing status
- Intermediate result
- Final result
- Error result

One request may produce multiple responses.

Responses must be delivered in sequence.

A response must remain available until it is explicitly acknowledged by MT5.

### 7. Sequential ACK Protocol

MT5 consumes responses in order.

After successfully receiving and processing a response, MT5 acknowledges its response sequence.

The server records the highest continuously acknowledged response sequence.

Responses must not be deleted before their acknowledgment is durably recorded.

Repeated ACK messages must be safe and idempotent.

If an ACK response is lost, MT5 may repeat the same ACK.

The server must return the existing acknowledgment state without causing side effects.

### 8. Three Different Acknowledgment Levels

The following states must never be confused:

1. HTTP 200: HTTP communication succeeded.
2. Request Registered: Python durably stored the request.
3. Response Acknowledged: MT5 consumed the response and confirmed it.

HTTP 200 alone does not prove that the requested operation was executed.

### 9. Recovery Rules

After an MT5 restart:

1. Load the persistent request counter.
2. Restore unresolved requests.
3. Restore the last acknowledged response sequence.
4. Resume response polling.
5. Retry unresolved requests using their original IDs.

After a Python restart:

1. Restore pending requests from durable storage.
2. Restore unacknowledged responses.
3. Resume incomplete processing safely.
4. Continue response delivery from the last acknowledged sequence.

After a Laravel restart:

1. Restore any durably accepted but undelivered requests.
2. Resume forwarding them to Python.
3. Never report a request as delivered without Python registration confirmation.

### 10. Idempotency

The same request ID must never cause an operation to execute twice.

Python must return the existing request status or result when it receives a duplicate request ID.

Database commands must also be designed for safe retries.

For example, repeated insertion of the same candle must not create duplicate records.

### 11. Local and Server-Side Cleanup

MT5 may remove a request from its unresolved request file only after the required completion and acknowledgment conditions are satisfied.

Python may remove or archive a response only after its ACK has been durably recorded.

The system should retain only unresolved requests and unacknowledged responses in its active queues.

Cleanup must never remove the only durable copy of an unresolved operation.

### 12. Error Classification

MT5 must classify DLL and HTTP errors.

Each error category must define:

- Whether the request may have reached the server
- Whether retry is safe
- Whether the original request ID must be reused
- Retry delay
- Maximum retry policy
- Recovery action

A communication error must never automatically be interpreted as proof that the server did not execute the request.

### 13. Failure Testing

The implementation must be tested under these conditions:

- Internet disconnected before transmission
- Internet disconnected during transmission
- Internet disconnected after server registration
- Response lost during delivery
- ACK lost during delivery
- MT5 restarted with unresolved requests
- Laravel restarted during forwarding
- Python restarted during request processing
- Python restarted after generating a response
- Server power failure before and after database commit
- Duplicate request delivery
- Duplicate ACK delivery
- Multiple responses for one request
- Recovery of response sequence after restart

### 14. Core Guarantee

The system must prioritize durable delivery and safe recovery over speed.

A request must remain recoverable until its outcome is known.

A response must remain recoverable until MT5 acknowledges it.

No component may assume that a message was delivered merely because it attempted to send it.

The protocol must be sequential, persistent, idempotent and restart-safe.
