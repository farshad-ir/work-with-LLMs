بسیار خوب. حالا ماشین حالت را طوری طراحی می‌کنیم که قطع ارتباط، خاموش‌شدن MT5، Retry و حتی بسته‌شدن ناگهانی ترمینال باعث گم‌شدن درخواست نشود.

یک اصل را در تمام طراحی حفظ می‌کنیم:

**فایل درخواست، مرجع اصلی وضعیت است؛ نه حافظه MT5 و نه نتیجه آخرین فراخوانی DLL.**

### ۱. ساختار نهایی پرونده هر درخواست

مثلاً `request_101.ini`:

```ini
[request]
client_id = mt5_terminal_01
request_id = mt5_terminal_01-000001
serial = 101
created_at = 2026-11-15T12:30:00Z
status = CREATED

[delivery]
send_attempts = 0
last_send_result =

[response]
response_id =
status =
payload_file =

[ack]
ack = 0
attempts = 0
```

فایل پاسخ JSON نیز در همان پوشه نگهداری می‌شود؛ مثلاً:

`request_101_response.json`

### ۲. ماشین حالت

این مراحل را پیشنهاد می‌کنم:

| مرحله | وضعیت | عملیات |
|---|---|---|
| ۱ | CREATED | ایجاد و ذخیره درخواست |
| ۲ | SENDING | آماده‌سازی و ارسال |
| ۳ | SENT | ارسال از دید DLL انجام شده |
| ۴ | REGISTERED | ثبت پایدار در Python تأیید شده |
| ۵ | PROCESSING | درخواست در Python در حال پردازش است |
| ۶ | COMPLETED | پاسخ موفق دریافت شده |
| ۷ | FAILED | پاسخ خطا دریافت شده |
| ۸ | ACK_SENDING | ارسال تأیید دریافت |
| ۹ | ACKNOWLEDGED | تأیید نهایی Python دریافت شده |
| ۱۰ | DELETED | پرونده درخواست حذف شده |

نکته: `COMPLETED` و `FAILED` هر دو باید به مرحله ACK برسند.

### ۳. نکته بسیار مهم درباره Retry و سریال

با توجه به سورس DLL که بررسی کردم، تابع `SendLatestJson()` از محتوای فایل SHA-256 می‌سازد و اگر محتوای جدید با آخرین ارسال موفق یکسان باشد، ارسال را با نتیجه `204` رد می‌کند.

از طرف دیگر، پروتکل می‌گوید اگر `request_id` یکسان با محتوای متفاوت برسد، درخواست باید رد شود.

پس باید یک اصلاح مهم در طراحی داشته باشیم:

- `request_id` و `payload` در تمام Retryها ثابت می‌مانند.
- `serial` با هر تلاش ارسال افزایش می‌یابد.
- سریال را به‌عنوان **شناسه تلاش ارسال** تعریف می‌کنیم، نه بخشی از محتوای منطقی درخواست.
- Backend هنگام تشخیص تکراری بودن درخواست، سریال تلاش را از مقایسه محتوای درخواست مستثنا می‌کند.

این موضوع باید در نسخه اصلاح‌شده پروتکل ثبت شود.

### ۴. نام‌گذاری فایل‌ها

یک اصلاح دیگر: نام فایل باید بر اساس `request_id` باشد، نه `serial`؛ چون سریال با Retry تغییر می‌کند ولی هویت درخواست ثابت است.

مثلاً:

```text
Gateway/
│
├── config.ini
│
├── temp/
│   ├── request_mt5_terminal_01-000001.ini
│   ├── request_mt5_terminal_01-000001_response.json
│   │
│   ├── request_mt5_terminal_01-000002.ini
│   └── request_mt5_terminal_01-000002_response.json
│
└── archive/
```

پوشه `archive` اختیاری است؛ فعلاً می‌توانیم بعد از ACK فایل‌ها را حذف کنیم.

### ۵. بازیابی پس از راه‌اندازی مجدد MT5

هنگام اجرای اکسپرت:

1. `config.ini` خوانده می‌شود.
2. تمام فایل‌های `temp` بررسی می‌شوند.
3. درخواست‌ها بر اساس زمان ایجاد مرتب می‌شوند.
4. قدیمی‌ترین درخواست تعیین می‌شود.
5. وضعیت ذخیره‌شده آن بررسی می‌شود.
6. ماشین حالت از همان مرحله ادامه می‌دهد.

هیچ درخواست جدیدی نباید باعث فراموش‌شدن درخواست قبلی شود.

### ۶. تقسیم مسئولیت توابع

برای اینکه تابع مرکزی بیش از حد پیچیده نشود، این تقسیم را پیشنهاد می‌کنم:

| تابع | مسئولیت |
|---|---|
| `GatewaySubmit(body)` | ایجاد پرونده درخواست جدید |
| `GatewayPump()` | اجرای یک مرحله از ماشین حالت |
| `LoadGatewayState()` | خواندن تنظیمات و درخواست‌های معوق |
| `SaveRequestState()` | ذخیره وضعیت درخواست |
| `ProcessGatewayResponse()` | اعتبارسنجی و ذخیره پاسخ |
| `ProcessGatewayAck()` | ارسال ACK و بررسی نتیجه |

`GatewaySubmit` فقط یک ورودی می‌گیرد: JSON Body.

`GatewayPump` در `OnTimer` اجرا می‌شود و ماشین حالت را جلو می‌برد؛ بنابراین MT5 هنگام انتظار برای پاسخ مسدود نمی‌شود.

---

**پیشنهاد من برای ادامه:** پیش از نوشتن کد، باید قرارداد دقیق `serial` و Retry را به پروتکل اضافه کنیم و رفتار ACK را با Endpointهای واقعی تطبیق دهیم. به‌خصوص DLL فعلی پاسخ HTTP مربوط به POST را به MQL5 برنمی‌گرداند؛ بنابراین باید مسیر دریافت و تأیید `ACKNOWLEDGED` را دقیقاً مشخص کنیم.
