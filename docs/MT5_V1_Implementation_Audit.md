## ۱. خلاصه مدیریتی

اکسپرت فعلی بخش مهمی از زیرساخت تحویل مطمئن پیام را پیاده کرده است.

موارد پیاده‌شده:

- تولید شناسه یکتای درخواست.
- ذخیره درخواست پیش از ارسال.
- حفظ شناسه و محتوای درخواست در Retry.
- بازیابی درخواست حل‌نشده پس از راه‌اندازی مجدد.
- ارسال درخواست از طریق DLL.
- دریافت وضعیت پردازش از طریق Poll.
- اعتبارسنجی هویت پاسخ.
- ذخیره پاسخ نهایی روی دیسک.
- پشتیبانی از پاسخ‌های `COMPLETED` و `FAILED`.
- ارسال ACK با شناسه پاسخ.
- اعتبارسنجی `ACK_RESULT`.
- پاک‌سازی فایل‌ها پس از تأیید ACK.
- بازگشت ماشین حالت به IDLE.

اما هنوز اکسپرت، کل فرایند کاربردی تعریف‌شده در مستندات MT5–Python–SQLite را اجرا نمی‌کند.

مهم‌ترین شکاف‌ها:

1. ساختار JSON فعلی اکسپرت با قرارداد ورودی Python مطابقت ندارد.
2. پاسخ نهایی ذخیره می‌شود، اما محتوای کاربردی آن مصرف و پردازش نمی‌شود.
3. آماده‌سازی H1/H6 مطابق برنامه راه‌اندازی کامل نشده است.
4. کشف جدول‌های SQLite و بررسی داده‌های موجود در چرخه اکسپرت وجود ندارد.
5. Retryها محدود به مدت اجرای `OnInit` هستند و پس از پایان ناموفق، چرخه خودکار ادامه پیدا نمی‌کند.
6. قرارداد مستندات پروتکل و برخی مستندات قدیمی با پیاده‌سازی Python کاملاً یکسان نیست.

**نتیجه:** زیرساخت تحویل پیام پیشرفت خوبی دارد، اما انطباق کامل با کاربرد نهایی نسخه یک هنوز حاصل نشده است.

## ۲. وضعیت ماشین حالت و تحویل پیام

### ۲.۱. ساختار وضعیت‌ها

در `tests/log.Sender_MT5` خطوط ۷۱ تا ۸۲ این وضعیت‌ها تعریف شده‌اند:

| وضعیت | معنی | وضعیت پیاده‌سازی |
|---|---|---|
| IDLE | آماده دریافت درخواست جدید | پیاده شده |
| CREATED | آغاز ساخت درخواست | پیاده شده |
| SENDING | ارسال درخواست | پیاده شده |
| SENT | ارسال HTTP موفق | پیاده شده |
| PROCESSING | انتظار برای پردازش Python | پیاده شده |
| RESPONSE_RECEIVED | پاسخ نهایی دریافت و ذخیره شده | پیاده شده |
| ACK_SENDING | ارسال تأیید دریافت | پیاده شده |
| ACKNOWLEDGED | تأیید ACK از سرور | پیاده شده |
| ERROR | وضعیت توقف خطا | تعریف شده، اما استفاده محدود دارد |

ماشین حالت در خطوط ۱۴۶ تا ۲۳۴ پیاده شده است.

انتقال وضعیت‌ها پیش از اجرای عملیات بعدی در `GatewayTransitionAndSave` ذخیره می‌شود.

این طراحی با اصل ثبت پایدار وضعیت پیش از عملیات حساس سازگار است.

### ۲.۲. بازیابی پس از راه‌اندازی مجدد

تابع `GatewayRecoverState` در خطوط ۵۴۳ تا ۶۵۰:

- وجود فایل درخواست را بررسی می‌کند.
- درخواست قبلی را بارگذاری می‌کند.
- پاسخ ذخیره‌شده را اعتبارسنجی می‌کند.
- اگر پاسخ نهایی وجود داشته باشد، وضعیت را به RESPONSE_RECEIVED ارتقا می‌دهد.
- اگر درخواست وجود داشته باشد ولی state برابر IDLE باشد، آن را به SENDING ارتقا می‌دهد.
- در وضعیت ACKNOWLEDGED اجازه ادامه پاک‌سازی را می‌دهد.

این بخش از نقاط قوت فعلی پیاده‌سازی است.

### ۲.۳. شناسه درخواست

تابع `GatewayNextRequestId` در خطوط ۶۵۵ تا ۶۹۰ شماره توالی را در فایل مستقل نگهداری می‌کند.

شناسه به شکل زیر ساخته می‌شود:

`client_id-sequence`

تابع `GatewayPrepareRequest` در خطوط ۶۹۳ تا ۷۷۳ نیز اگر درخواست قبلی موجود باشد، همان درخواست را بازیابی می‌کند و درخواست جدید نمی‌سازد.

این رفتار با قانون حفظ `request_id` در Retry مطابقت دارد.

**نکته قابل بررسی:** مقدار پیش‌فرض `InpGatewayClientId` ثابت است. اگر چند ترمینال یا چند نمونه اکسپرت از یک پوشه Common مشترک و یک client_id استفاده کنند، امکان تداخل فایل‌ها و شماره توالی وجود دارد. یکتایی client_id برای هر ترمینال باید تضمین شود.

### ۲.۴. ارسال درخواست

تابع `GatewaySendRequest` در خطوط ۷۷۵ تا ۸۱۹:

1. فایل درخواست پایدار را باز می‌کند.
2. همان Envelope ذخیره‌شده را می‌خواند.
3. آن را در فایل Feed مورد انتظار DLL قرار می‌دهد.
4. `SendLatestJson()` را اجرا می‌کند.
5. کد HTTP را برمی‌گرداند.

کدهای HTTP در بازه ۲۰۰ تا ۲۹۹ موفق تلقی می‌شوند.

این موضوع برای پاسخ‌هایی مانند ۲۰۲ و ۲۰۴ مناسب است؛ اما هنوز پاسخ `INGEST_RESULT` از نظر محتوای JSON و هویت درخواست در MT5 اعتبارسنجی نمی‌شود.

در نتیجه، MT5 فعلاً موفقیت HTTP را مبنای ورود به SENT قرار می‌دهد، نه اعتبارسنجی کامل پیام REGISTERED.

### ۲.۵. Poll

تابع `GatewayPoll` در خطوط ۸۶۴ تا ۸۷۶ درخواست Poll را می‌سازد.

تابع `GatewayParsePollResponse` در خطوط ۸۷۸ تا ۹۴۰ موارد زیر را بررسی می‌کند:

- protocol
- version
- message_type
- client_id
- request_id
- status
- وجود response_id برای پاسخ نهایی

وضعیت‌های قابل قبول:

- PROCESSING
- COMPLETED
- FAILED

این بخش با پروتکل نسخه یک سازگار است.

در پروتکل، REGISTERED یک وضعیت سمت Python است. پیاده‌سازی MT5 وضعیت مستقل REGISTERED ندارد و پس از SENT مستقیماً Poll می‌کند. Python در صورت آماده نبودن پاسخ، PROCESSING برمی‌گرداند.

این ساده‌سازی قابل قبول است، مشروط بر اینکه تفاوت SENT و REGISTERED در منطق سیستم حفظ شود.

### ۲.۶. ذخیره پاسخ

تابع `GatewayPollAndPersist` در خطوط ۹۶۹ تا ۱۰۱۵ پاسخ نهایی را پیش از انتقال وضعیت ذخیره می‌کند.

این رفتار بسیار مهم است؛ زیرا اگر MT5 بعد از دریافت پاسخ خاموش شود، پاسخ محلی باقی می‌ماند و در اجرای بعدی می‌تواند بازیابی شود.

### ۲.۷. ACK

تابع `GatewaySendAck` در خطوط ۱۱۹۲ تا ۱۲۴۰:

- response_id را از پاسخ ذخیره‌شده استخراج می‌کند.
- درخواست ACK را می‌سازد.
- پاسخ سرور را دریافت می‌کند.
- `ACK_RESULT` را اعتبارسنجی می‌کند.
- client_id، request_id، response_id و status را تطبیق می‌دهد.

این قسمت با قرارداد ACK نسخه یک سازگار است.

### ۲.۸. پاک‌سازی

تابع `GatewayCleanup` در خطوط ۱۲۴۲ تا ۱۲۷۱ فایل درخواست و پاسخ را حذف می‌کند.

پاک‌سازی فقط پس از ACKNOWLEDGED انجام می‌شود.

پس از موفقیت پاک‌سازی، وضعیت به IDLE برمی‌گردد.

این بخش در اجرای واقعی گزارش‌شده نیز موفق بوده است.

## ۳. شکاف مهم: پاسخ دریافت می‌شود، اما مصرف نمی‌شود

این مهم‌ترین مسئله در معماری فعلی است.

در پروتکل نسخه یک، MT5 پس از دریافت و مصرف پاسخ باید ACK ارسال کند.

اما در پیاده‌سازی فعلی:

1. پاسخ نهایی دریافت می‌شود.
2. پاسخ در `current_response.json` ذخیره می‌شود.
3. ماشین حالت مستقیماً به ACK_SENDING می‌رود.
4. ACK ارسال می‌شود.
5. فایل پاسخ حذف می‌شود.

تابع مستقلی برای پردازش محتوای `payload` پاسخ وجود ندارد.

برای مثال، اگر Python پاسخ زیر را برگرداند:

```json
{
  "operations": [
    {
      "command": "LIST-TABL",
      "result": {
        "tables": ["mt5_candles", "mt5_messages"],
        "count": 2
      }
    }
  ]
}
```

اکسپرت فعلی این فهرست را استخراج نمی‌کند و در هیچ متغیر یا ساختار کاربردی نگهداری نمی‌کند.

در نتیجه، پس از ACK و حذف فایل، نتیجه عملیات دیگر در MT5 در دسترس نیست.

### تصمیم معماری موردنیاز

باید یک مرحله مشخص بین RESPONSE_RECEIVED و ACK_SENDING اضافه شود:

`RESPONSE_RECEIVED → RESPONSE_PROCESSED → ACK_SENDING`

این مرحله باید:

- JSON پاسخ را بخواند.
- نتیجه عملیات را اعتبارسنجی کند.
- نتیجه را به ساختار کاربردی MT5 منتقل کند.
- موفقیت پردازش را به‌صورت پایدار ثبت کند.
- سپس اجازه ACK بدهد.

پاسخ FAILED نیز باید به‌عنوان یک نتیجه نهایی پردازش شود و سپس ACK دریافت کند.

## ۴. شکاف مهم: ساختار درخواست MT5 با قرارداد Python

### ۴.۱. JSON فعلی اکسپرت

در `tests/log.Sender_MT5` خطوط ۳۶۳ تا ۳۶۹، بدنه فعلی تقریباً به این شکل ساخته می‌شود:

```json
{
  "H1": {
    "candles": []
  }
}
```

### ۴.۲. قرارداد Python

در `app/mt5_delivery.py` خطوط ۸۴ تا ۱۴۰، تابع `_validate_envelope` انتظار دارد:

- payload یک object باشد.
- payload دارای command باشد.
- command یکی از INIT یا CANDLE_UPDATE باشد.
- برای INIT، آرایه operations وجود داشته باشد و خالی نباشد.

در خطوط ۳۱۳ تا ۳۵۰ همین فایل، پردازش فعلی فقط INIT را اجرا می‌کند.

بنابراین ساختار فعلی بدنه اکسپرت با قرارداد ورودی Python مطابقت ندارد.

### ۴.۳. نکته مهم درباره لاگ موفق اخیر

در لاگ اخیر این پیام وجود داشت:

`Pending request recovered. request_id=mt5_terminal_01-000001`

این پیام نشان می‌دهد اکسپرت یک درخواست موجود را بازیابی کرده است.

در `GatewayPrepareRequest`، وقتی فایل درخواست موجود باشد، بدنه جدید نادیده گرفته می‌شود و همان Envelope قبلی استفاده می‌شود.

بنابراین اجرای موفق اخیر ثابت می‌کند که مسیر بازیابی و تحویل درخواست قبلی درست کار کرده است؛ اما ارسال بدنه جدید فعلی را تأیید نمی‌کند.

**این اختلاف باید پیش از اعلام موفقیت کامل ارتباط MT5 با Python برطرف شود.**

## ۵. وضعیت آماده‌سازی داده‌های H1 و H6

طبق سند `docs/MT5-Python-SQLite.md`، برنامه راه‌اندازی شامل:

- ۱۰۰ کندل بسته‌شده H1
- ۲۰ کندل بسته‌شده H6
- Feed مستقل برای هر دو جریان
- پردازش زمانی از قدیمی به جدید
- اطمینان از عدم Feed تکراری

است.

اما در `OnInit` فعلی، خطوط ۲۸۳ تا ۳۸۱:

1. داده H1 کپی می‌شود.
2. داده H6 کپی می‌شود.
3. فقط حلقه H1 اجرا می‌شود.
4. حلقه Feed برای H6 وجود ندارد.
5. فقط بخش H1 در JSON ساخته می‌شود.

چند مسئله مشخص:

- تعداد کپی‌شده H1 و H6 فقط از نظر بزرگ‌تر بودن از صفر بررسی می‌شود؛ کامل بودن ۱۰۰ و ۲۰ کندل تضمین نشده است.
- حلقه H1 از `h1Copied - 1` تا `1` اجرا می‌شود و index صفر را پردازش نمی‌کند.
- داده H6 کپی می‌شود، اما در Feed و JSON استفاده نمی‌شود.
- Reset مستقل دو Bifurcation پیش از Warm-up در این مسیر دیده نمی‌شود.

بنابراین بخش Warm-up هنوز با برنامه نهایی مستندات منطبق نیست.

این موضوع باید مستقل از Gateway اصلاح و آزمایش شود.

## ۷. مدیریت قطع ارتباط و Retry

در کد فعلی:

| عملیات | حداکثر تلاش در هر اجرای تابع |
|---|---:|
| Send | ۵ |
| Poll | ۶۰ |
| ACK | ۵ |
| اجرای کل ماشین حالت | ۱۲۰ مرحله |

مکث فعلی یک ثانیه است.

این محدودیت‌ها از حلقه بی‌نهایت در یک اجرای تابع جلوگیری می‌کنند.

اما یک محدودیت معماری وجود دارد:

`GatewayExecuteRequest` در `OnInit` اجرا می‌شود.

`OnTick` خالی است و OnTimer وجود ندارد.

اگر حداکثر تلاش‌ها تمام شوند، تابع false برمی‌گرداند و `OnInit` نیز INIT_FAILED می‌دهد.

در این وضعیت، درخواست روی دیسک باقی می‌ماند؛ اما ادامه خودکار Retry در چرخه‌های بعدی تضمین نشده است. معمولاً برای ادامه، اجرای مجدد اکسپرت یا راه‌اندازی مجدد آن لازم خواهد بود.

این رفتار با الزام مستندات برای بازیابی مستمر در چرخه‌های بعدی تفاوت دارد.

با توجه به تصمیم پروژه مبنی بر استفاده از Sleep و نداشتن Timer، باید این محدودیت به‌عنوان رفتار رسمی نسخه فعلی ثبت شود و سیاست اجرای مجدد پس از پایان ناموفق مشخص شود.

## ۸. اعتبارسنجی خطاهای HTTP

تابع `GatewayHttpGet` در خطوط ۸۲۴ تا ۸۵۹، هر نتیجه مثبت را به‌عنوان دریافت پاسخ در نظر می‌گیرد و سپس JSON را بررسی می‌کند.

در صورت دریافت پاسخ HTTP خطا، ممکن است DLL یک کد مثبت مربوط به HTTP برگرداند.

در نتیجه، خطای HTTP لزوماً به‌صورت مستقل از خطای شبکه تشخیص داده نمی‌شود.

در مسیر فعلی، پاسخ نامعتبر نهایتاً در اعتبارسنجی JSON یا Envelope رد می‌شود؛ اما خطاهای دائمی مانند ۴۰۰ یا ۴۰۴ ممکن است در دسته خطای عمومی Poll قرار بگیرند و دوباره Retry شوند.

اصلاح پیشنهادی:

- تفکیک خطای شبکه از خطای HTTP.
- تفکیک خطاهای موقت از خطاهای دائمی.
- ثبت کد و متن خطا.
- جلوگیری از Retry بی‌فایده برای خطاهای دائمی مانند ساختار نامعتبر درخواست.

## ۹. اختلاف مستندات با پیاده‌سازی

چند سند موجود باید در آینده هم‌راستا شوند:

### پروتکل JSON نسخه یک

این سند رابطه یک درخواست با یک پاسخ نهایی را تعریف می‌کند.

### MT5 Reliable Delivery Protocol

این سند در بخش Response Queue از چند پاسخ، response_sequence و تحویل ترتیبی صحبت می‌کند.

این دو مدل یکسان نیستند.

برای نسخه یک باید مدل One-to-One سند JSON مرجع باشد؛ قابلیت چند پاسخ باید به نسخه بعدی موکول شود.

### MT5 State Machine

این سند از ساختار فایل‌ها و اجرای GatewayPump در OnTimer صحبت می‌کند.

پیاده‌سازی فعلی به‌جای آن از چند فایل ثابت و اجرای Sleep در OnInit استفاده می‌کند.

بنابراین این سند باید به‌عنوان سند طراحی قدیمی شناخته شود یا با معماری فعلی بازنویسی شود.

### قرارداد INIT

نمونه INIT در سند JSON نسخه یک شامل symbol و timeframes است.

اما اعتبارسنجی Python در حال حاضر برای INIT آرایه operations را اجباری می‌کند.

این دو قرارداد باید یکسان شوند.

## ۱۰. اولویت اصلاحات پیشنهادی

### اولویت صفر ــ اصلاح قرارداد درخواست

پیش از هر توسعه دیگر:

1. ساختار payload اکسپرت با `_validate_envelope` در Python یکسان شود.
2. مشخص شود INIT دقیقاً چه عملیات‌هایی را اجرا می‌کند.
3. یک درخواست تازه، بدون فایل pending قبلی، ارسال و آزمایش شود.
4. پاسخ REGISTERED و شناسه‌های آن اعتبارسنجی شوند.

تا زمانی که این مرحله انجام نشده، موفقیت مسیر بازیابی قبلی را نباید معادل موفقیت ارسال درخواست جدید دانست.

### اولویت یک ــ مصرف پاسخ

1. ایجاد مرحله پردازش پاسخ بین RESPONSE_RECEIVED و ACK_SENDING.
2. استخراج نتیجه هر operation.
3. ذخیره پایدار نتیجه موردنیاز MT5.
4. ACK فقط پس از موفقیت مصرف پاسخ.

### اولویت دو ــ تکمیل Warm-up

1. بررسی دقیق ۱۰۰ کندل H1.
2. بررسی دقیق ۲۰ کندل H6.
3. Reset مستقل Bifurcationها.
4. Feed کامل و دقیق از قدیمی به جدید.
5. جلوگیری از حذف کندل بسته‌شده جدیدتر.
6. تأیید آمادگی هر دو جریان.

### اولویت سه ــ کشف و بررسی SQLite

1. تعیین دیتابیس هدف.
2. اجرای READ-STAT.
3. اجرای LIST-TABL.
4. نگهداری فهرست جدول‌ها در MT5.
5. اجرای READ-DATA برای جدول‌های موردنیاز.
6. تصمیم‌گیری درباره INIT-DATA فقط در صورت نیاز.

### اولویت چهار ــ بازیابی و خطا

1. تعیین رفتار پس از اتمام تلاش‌های محدود.
2. طبقه‌بندی HTTP و Network Error.
3. آزمایش قطع ارتباط در هر مرحله.
4. آزمایش خاموش‌شدن MT5 پیش و پس از ACK.
5. بررسی هم‌زمانی چند ترمینال و یکتایی client_id.
